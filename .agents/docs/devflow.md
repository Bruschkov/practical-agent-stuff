# Devflow Package

## Read when
- Changing `pi-extensions/devflow/` or its contract tests.

## Package boundary
- The package manifest loads `index.ts` as a Pi extension.
- `backlog.md` is a package-local runtime dependency with the compatible range `^1.4.0`; use its locally installed CLI, not a Homebrew or other global installation.
- The lockfile records the resolved CLI and peer-dependency graph required by `npm ci`. Do not change the supported range without validating the CLI contract.
- For source-local development, run `npm ci --prefix pi-extensions/devflow` before loading it. Use `npm install --prefix pi-extensions/devflow` only to resynchronize the lockfile after a manifest change, then verify with `npm ci`.
- Controller commands use the package-local CLI; main-session refinement uses the `backlog` Pi tool rather than shell commands or Backlog.md internals. The tool has structured task/draft operations; task reads use the CLI JSON interface and draft reads use plain text.

## CLI contract
- Source-local test setup: `npm ci --prefix pi-extensions/devflow`.
- The contract test runs that local binary in a temporary Git repository.
- It verifies initialization/config lookup; task and draft create, read, update, archive; task parent/dependency data; task comments/assignees; and repeatable JSON for `task list` and `task view`.
- Backlog.md provides `--json` for task reads; draft reads use `--plain`.

## Backlog tool
- The extension registers one `backlog` tool. Its `operation` is one of `task_list`, `task_view`, `task_create`, `task_edit`, `task_archive`, `draft_list`, `draft_view`, `draft_create`, `draft_edit`, `draft_archive`, `draft_promote`, or `refinement_publish`.
- Use named fields, never raw CLI arguments: `id`, `title`, `description`, `status`, `priority`, `type`, `parent`, `dependsOn`, `assignees`, `labels`, `acceptanceCriteria`, `comment`, `commentAuthor`, `ready`, `limit`, and `proposedTasks` as applicable.
- Task reads request CLI JSON; drafts use `--plain`. Tool output is capped at 2,000 lines or 50 KB. Main-session model writes are queued on the project's `backlog/` directory and must use this tool; controller commands use the same package-local CLI directly.
- `task_create` supplies `Medium` when `priority` is absent. An edit must provide a changed field, and `commentAuthor` requires `comment`.

## Refinement
- `/refine` requires interactive mode. `/refine <idea-or-draft-id>` creates a draft or resumes a `DRAFT-<number>`; no-argument `/refine` selects an active draft or valid incoming backlog-handoff and reports handoff integration status and inbox count.
- Handoff integration is optional and has no package dependency. When `.backlog-handoff/config.json` and its registry are available, the workflow reads the current project's configured inbox (including `handoffDir`); unavailable or invalid setup leaves ordinary idea/draft refinement available.
- Selecting a handoff creates a draft containing its source path and complete original content. Preserve the generated `backlog-handoff` marker and handoff metadata while refining.
- The main session reads a resumed draft, persists accepted decisions, and proposes intent, concrete acceptance criteria, and a feature/sub-feature/task hierarchy with priorities and dependencies. It must not create or promote tasks while approval remains pending.
- After the user explicitly approves the displayed proposal, use `refinement_publish` with the draft ID and matching `proposedTasks`. It requires final interactive confirmation, validates proposal-local hierarchy/dependencies, creates tickets with explicit or `Medium` priority, records approval and published IDs in the draft, archives it, stages only `backlog/`, and commits with `git commit --only -- backlog`. Only after that commit does it move a linked handoff to `.backlog-handoff/processed/`; a move failure leaves the source in the inbox and reports it. Declining confirmation leaves the draft and handoff pending and creates no tickets.
- A failed refinement commit leaves the published backlog changes pending and the handoff in the inbox; do not rerun publication, which would duplicate tickets. After fixing the Git error, use interactive `/devflow-commit-backlog` to retry only the scoped `backlog/` commit.

## Git ownership
- The main-session refiner and child implementer must not run Git. Extension controller code owns Git operations.
- Refinement stages and commits only `backlog/`; `git commit --only` preserves any separately staged implementation files. Final feature approval stages only recorded implementation paths.
- The single-controller workflow does not add general same-worktree locks. A rare overlap that changes the staged tree aborts final feature approval for retry rather than committing unrelated paths.

## Session topology
- Refinement and implementation are independent entry points: `/refine` publishes backlog work but never starts implementation; `/implement-run` consumes compatible published tickets in the same or a later session.
- Use at most one `/implement-run` controller per Git worktree. Optional parallel interactive sessions may refine upcoming work or handle `/devflow-inbox`; scoped backlog commits and final-approval index checks protect unrelated implementation changes.
- The implementation-controller session owns final feature approval. It runs until completion or a persisted pause; it is not a permanent daemon.

## Implementation workers
- Core child-Pi runner and `/implement-run` behavior must work without `backlog-handoff`.
- `runChildPi` (exported by `pi-extensions/devflow/index.ts`) starts an isolated `pi --mode json -p --no-session` child in the project cwd. It loads this extension with `PI_DEVFLOW_WORKER=1`, inherits the selected model and thinking level, and lets Pi rediscover project context files and installed resources. It does not pass `--no-extensions`, so an installed project- or global-level `backlog-handoff` is available to the worker. A `readOnly` child additionally receives only `read`, `grep`, `find`, `ls`, `backlog`, and `complete_transition`, plus `PI_DEVFLOW_REVIEWER=1`.
- The runner consumes JSON `message_end` events, aggregates assistant usage, returns bounded final output and stderr (2,000 lines/50 KB), and reports non-zero exit, cancellation, invalid completion, or a missing `complete_transition` as a failure. Its result contains the validated `completed`, `needs_human`, `blocked`, or `failed` outcome when present.
- A child worker sets `PI_DEVFLOW_WORKER=1`. Only in that mode does the extension register `complete_transition`; it is the worker's single terminating final action and accepts only `completed`, `needs_human`, `blocked`, or `failed`.
- `implementerPrompt(taskId)` is exported from `index.ts`. It directs a worker to read that ticket with `backlog` `operation: "task_view"`, follow project instructions, implement only its criteria, run required checks, assess documentation/decision impact, avoid ticket-status changes and Git commits, emit JSON evidence (`summary`, `plan`, `modifiedFiles`, acceptance-criteria/check evidence, documentation impact, blockers), then terminate once. `completed` requires all criteria and required checks; human decisions use `needs_human`, external blockers use `blocked`, and all other failures use `failed`.
- `reviewerPrompt(taskId)` is exported from `index.ts`. It reviews the ticket, implementation evidence, and changed code without mutations, then returns JSON `{ "verdict": "approved"|"rework", "findings": string[] }`. Read-only workers cannot call mutating built-in tools and the `backlog` tool rejects writes when `PI_DEVFLOW_REVIEWER=1`; `completed` means the review itself completed, while the verdict controls follow-up.
- `reconcilerPrompt(featureId)` is exported from `index.ts`. After every descendant leaf is `Done`, it runs read-only and returns one persisted passed check for parent acceptance criteria, documentation, durable technical decisions, and related Backlog.md tickets. A clean reconciliation leaves the feature `In Review` pending final human approval; an unresolved decision follows the existing `Needs Human` protocol.
- `complete_transition` returns its outcome to the controller and does not mutate Backlog.md; the controller owns ticket status transitions.
- `/implement-run` without an ID requires interactive mode, lists features, and starts only the feature explicitly selected by the user; cancellation changes nothing. The picker places first and marks as recommended the feature containing the globally highest-ranked runnable leaf, shows that leaf plus its status and priority as rationale, and never auto-selects it. Recommendation uses the normal leaf order: `Rework`, configured priority, Backlog ordinal, then task ID. Its command completion offers feature IDs from the session-start Backlog.md snapshot and refreshes when the picker opens. `/implement-run <task-id>` accepts only a ready, unblocked, human-unowned leaf `task` in `Open` or `Rework`. `/implement-run <feature-id>` repeatedly discovers and runs eligible descendant leaves in `Rework` or `Open` until none remain, choosing each deterministically: `Rework`, configured priority (`Critical`, `High`, `Medium`, `Low`), Backlog ordinal, then task ID. It continues after a ticket becomes non-runnable through review, blocking, or deferred human input; a failed implementation remains `Open` and ends the invocation rather than retrying indefinitely. `Rework` is the only resume class; failed or cancelled `Open` work has no separate priority marker. It records `In Progress` before starting the worker. The controller requires the worker's JSON evidence, records its plan, acceptance-criteria and check evidence, documentation impact, blockers, usage, modified files, and final summary through Backlog.md, and checks met criteria. A `completed` result requires every criterion met and every reported check passed, then moves to `In Review` and launches the read-only reviewer; all other outcomes move to `Blocked`, `Needs Human`, or `Open` as applicable. On an implementation or review `needs_human`, it persists the request and assigns `@human` before prompting; an answer is stored as an `@human` comment, clears the assignment, and reopens the task. A cancelled or unavailable prompt leaves the persisted request in `Needs Human` for later resolution. A completed review is persisted as an `@reviewer` comment. `approved` moves the leaf to `Done`; `rework` moves it to `Rework` and immediately reruns the implementer with the review comments. Once every descendant leaf is `Done`, the controller reconciles and presents an interactive human with the feature and leaf summaries, check and reviewer evidence, reconciliation, and a staged Git diff limited to recorded descendant modified files. It refuses a pre-existing staged index, stages only validated recorded paths, and verifies the staged index did not change after review. Approval commits those staged paths, records the commit in an `@human` comment, marks feature acceptance criteria complete, and moves the feature to `Done`; no staged recorded changes simply skip the commit. Declining unstages the controller's paths, retains `In Review`, and optionally records feedback before continuing the main-session discussion; feedback alone does not trigger rework. A non-interactive run leaves the feature `In Review` and reports that approval requires the UI. Two rework attempts are allowed; a third rework verdict moves the task to `Needs Human`, assigns `@human`, and records the cap diagnostic. Malformed or failed implementation runs return a started task to `Open` with a workflow comment.
- Installed `backlog-handoff` is inherited through normal Pi extension discovery, so workers can route discovered cross-project work. Do not add a dependency, detection, adapter, or dedicated test for it.

## Feature-selection fixtures
- `selectRunnableFeatureTask` selects the next leaf within a feature; `recommendRunnableFeature` selects the recommended feature/leaf pair. Both consume the Backlog.md `task list --json` payload and are fixture-tested seams.
- `tests/pi-extensions/devflow/fixtures/selection-*.json` are package-local CLI snapshots covering nested hierarchy, cross-feature recommendation, dependency readiness, `@human` exclusion, rework resume, configured priority, and Backlog ordinal ordering. Preserve their real CLI shape when changing selection or upgrading Backlog.md.

## Human-request inbox
- `/implement-run` prompts immediately after persisting a human request when UI is available. Dismissed or unavailable prompts remain resumable in `Needs Human`.
- `/devflow-inbox` is a manual recovery entry point, not a required daemon or dedicated session. From any interactive Pi session, it lists `Needs Human` tickets, lets the user select one, and shows its latest persisted `@workflow` request.
- A non-empty response is recorded as an `@human` comment, clears `@human`, and reopens the ticket to `Open`. Cancelling or submitting no response leaves it in `Needs Human`; rerun `/implement-run` when no active feature controller remains to resume it.

## Workflow configuration
- The required types, statuses, priorities, refinement approval boundary, HITL handling, and Definition of Done are defined by [Adopt a Backlog.md workflow contract](decisions/2026-09-03-adopt-backlog-workflow-contract.md).
- `/devflow-init` is interactive and requires Git. It operates at the Git top level, initializes an absent Backlog.md project only after confirmation, and reconfirms before changing an existing configuration.
- It reconciles `default_status` (`Open`), the required status/type/priority lists, and `definition_of_done` in the discovered project YAML. It supports `backlog.config.yml`, `backlog/config.yml`, and `.backlog/config.yml`; other locations fail clearly rather than being changed blindly.
- `backlog config set` cannot write list-valued `statuses`, `types`, or `priorities`; `/devflow-init` validates its YAML changes through package-local `backlog config get`. Backlog.md exposes `definition_of_done` as `definitionOfDone` in that command. It has no configurable default priority, so workflow ticket creation must pass `Medium` explicitly when none is selected.
